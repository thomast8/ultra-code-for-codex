name: ultra-code
description: Orchestrate substantive work through Ultra workflows while the selected chat owns intent, review, and delivery.
---

Use Ultra for substantive work when explicitly requested or active in the verified turn. Resolve the exact current `ultra_context` handle before starting. Keep the selected lead model and effort. If worker capability is blocked, report the blocker; do not substitute native subagents. Plan mode is read-only. All repository quality, permission, and user scope rules still apply.

Read [the generated authoring reference](references/authoring.md) before writing a workflow. Use contract version 2: `agent(prompt, options?)`, optional schemas, host-owned capacity and workspace claims. The script is JavaScript, not prose. Use `ultra_start`; confirm its saved run ID with `ultra_status`. Use `ultra_result` for complete results, `ultra_inspect` for owned local histories, and `ultra_wait` for meaningful changes. Open `ultra_panel` only when a panel is useful.

The installed reference defines the active API even when working on an older plugin checkout. For authorized edits use `access: "workspace-write"`; the default is `"read-only"`. A returned run ID confirms creation only. Check `ultra_status` for dispatched workers before claiming they started.

Understand the outcome before dispatch. Assign independent work together when each result will help, and keep dependent decisions with the lead between phases. A coupled edit can use one writer. Never invent extra workers to fill the three shared slots. Give each worker the full task and enough source context. Workers cannot read the run's objective or acceptance list, the lead's chat history, or MCP tools.

Ordinary lookup, truncation or command mistakes can be corrected inside the same assignment, at most twice for the same failed operation. A failed, truncated or locally sandbox-denied tool or shell command inside a still-running worker is not a workflow execution or dispatch failure; do not strengthen a user's workflow-failure stop rule into a command-failure stop rule. A local operation-not-permitted or read-only-filesystem result is a recoverable tool limitation unless required task access itself was revoked or is absent. Let that worker correct the operation with a smaller, corrected or permitted command. An invalid agent dispatch, terminal worker failure, unverifiable or lost required authority, replacement, corrective workflow, or operator repair fails the first attempt. Preserve old attempts and evidence. Do not automatically repeat uncertain work; verify termination and any possible writes before releasing its reservation. A returned worker is not accepted work.

The host creates a final review handoff when a new run ends with unreviewed worker work. Claim it, check results and the diff, and complete required checks that worker permissions prevented before resolving acceptance with evidence. Explicit lead(...) calls still allow decisions between phases. Distinguish local tests, real workflow QA, and deployed behavior. Disclose gaps instead of declaring success from a completed process. If a repair is authorized, use a separate linked attempt and keep the original verdict.
