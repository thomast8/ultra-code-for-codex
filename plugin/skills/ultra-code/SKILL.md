name: ultra-code
description: Orchestrate substantive Ultra work through quality-first dynamic workflows. Preserve the selected lead for intent, synthesis, verified completion and consequential actions.
---

Use this skill for explicit Ultra Code requests or verified Ultra turns. While Ultra is active, author and run a workflow for substantive research, planning, review and implementation. Keep conversation and trivial mechanical edits direct. Optimize for correct, well-supported and complete work within the user's scope and explicit limits; minimizing tokens or agent calls is not the objective.

When Ultra delegates, use the workflow engine through `ultra_start`. Do not use native subagents or another delegation tool instead, including for planning, research or review. If the engine or required worker capability is unavailable, report the blocker; do not fall back to native subagents. Opening the panel does not start a workflow. Verify a saved run ID with `ultra_status` before claiming Ultra delegated work, then inspect the saved results and resolve required lead handoffs before claiming completion.

Before starting, resolve the exact current `ultra_context` handle. Preserve the selected lead model and effort. Unknown context blocks execution; Plan Mode remains read-only. Existing task scope, repository quality gates and approval requirements still apply.

Call `ultra_panel` with the verified `contextKey` when a panel is needed. Its built-in display guard uses a browser-owned lock scoped to the verified profile and chat: an already-open panel is reused without promoting another tab. The lock releases when that panel closes. Repeated opener calls do not rely on the lead remembering to inspect tabs first. Reuse the existing dashboard for subsequent workflow work; it refreshes across turns.

The supported host must provide Web Locks and a fullscreen display mode for automatic opening. If the guard cannot safely claim the panel, it stays inline and reports the limitation; do not force another tab or substitute private host APIs. Inspect the supported browser inventory for visual QA and never claim the panel opened without host confirmation. Do not ask the user to send a binding message when verified chat routing is available.

In Plan Mode, produce an Ultra plan: use read-only workflows to investigate independent questions and challenge the proposed design. The selected lead resolves choices and synthesizes an implementation-ready plan from repository evidence. Do not implement the plan, edit project files, dispatch writing workers or publish changes.

The plan must state the outcome and acceptance criteria, the evidence behind the chosen design, precise interfaces and behavior, ordered file-level changes, dependencies, verification and stop conditions. Surface unresolved decisions explicitly. Use `kind: "planning"` for read-only lead handoffs and resolve them only against the plan's acceptance criteria; planning completion does not establish implemented or production-verified behavior. Choose phases and quality patterns for the task; there is no fixed team or mandatory stage sequence.

1. Decompose the outcome into source partitions, independent approaches, dependencies and verification questions before dispatch. Prepare independent assignments together and let the lead progress interpretation or integration alongside them. Do not default to one worker for an entire separable corpus. A coupled implementation may use one writer; independent investigation and verification still deserve consideration. Do not invent work to fill slots or duplicate a completed factual investigation.
2. Workers inherit the run's captured lead model and effort when those fields are omitted. Prefer this default. Override either field only for a clear task-specific reason, recorded in the assessment; routine mechanical work may justify a different tier. The backend verifies availability and exact effective routing. An unavailable inherited or explicit pair blocks dispatch; never substitute silently or repeatedly retry a blocked pair.
3. Provide all six assignment fields: outcome, bounded inputs, ownership, constraints, acceptance and stop conditions. Record the seven assessment fields before dispatch and retain them unchanged. Pass source references and relevant extracts, not the parent chat. Reuse completed evidence rather than commissioning the same investigation again.
4. Bound `maxAgentCalls` for the chosen investigations, verifiers, critics, additional rounds and authored retries. This ceiling is not a default of one or a target to exhaust. Reserve only the lead and observed occupied slots, with evidence; never reserve an unused spare to serialize independent work. Honor user budgets, quotas and scope limits. Concurrent workflows share local admission, not a host-wide reservation. No observed capacity means no invented grant. An observed-token threshold blocks later admission but does not cap an active worker's generation or monetary cost.
5. Record the dispatch plan with `log()` at the start of the immutable script: assignments, dependencies, why their division is useful, capacity reservations and any reason to select only one worker. State the next lead action in chat. Start the script, then use `ultra_wait` across its run IDs. Read results on meaningful changes, completion, errors or lead handoffs. UI polling does not require model calls. Do not turn quiet progress into repeated lead inference or assume silence means a hang.

   Prefer `pipeline(items, async (item, index) => { ... })` for independent items with dependent stages: investigate an item, inspect execution and acceptance, then verify that accepted finding without waiting for unrelated items. Use `parallel()` for independent ready assignments, and a barrier only when the next stage needs the complete cross-item set. Batch independent starts when separate workflows fit. Verify actual start times before claiming parallel execution.

6. Build verification into substantive work. Try to disprove important findings against original sources or reproduction evidence; use distinct lenses for different failure modes. Compare independent approaches when the solution space warrants it. For broad work, check completeness against the original requirements and source inventory, then investigate named gaps or new evidence within the declared bound. Disclose unread sources, dropped items and stopping limits. Repeated agreement is not proof; uncertainty is not refutation. Read the authoring reference's quality patterns rather than inventing a fixed critic team.
7. Keep judgment, required real QA, review, integration and consequential actions with the selected lead. Claim a handoff when inspection begins and resolve it promptly after acceptance checks; do not claim early or leave a finished review pending during unrelated work. Distinguish execution from goal acceptance. Uncertain workers require actual termination/write readback; no automatic replacement. Preserve incomplete results and return the resolved lead decision unchanged.

Worker failures, uncertainty, incomplete acceptance and verification always return to the lead. A panel handoff is never a request for the user to review worker output. Resolve it yourself or preserve an explicit incomplete outcome. Ask the user directly in chat only when an actual decision, missing information or authority is necessary; do not delegate routine verification to them or leave a pending handoff as their next step.

Read [the authoring reference](references/authoring.md) before writing a script. Its APIs and examples describe the implemented runtime. They do not grant missing authority or establish live QA for a particular installation.
