---
name: ultra-code
description: Run bounded, cost-aware workflows when independent work warrants orchestration. Preserve the selected Codex lead for intent, decisions, integration, verification and consequential actions.
---

Use this skill for explicit Ultra Code requests or verified Ultra turns when a task benefits from independent workers. A small, tightly coupled task should stay with the lead. Ultra is permission to consider orchestration, not a requirement to create workers.

When Ultra delegates, use the workflow engine through `ultra_start`. Do not use native subagents or another delegation tool instead, including for planning, research or review. If the engine or required worker capability is unavailable, report the blocker; do not fall back to native subagents. Opening the panel does not start a workflow. Verify a saved run ID with `ultra_status` before claiming Ultra delegated work, then inspect the saved results and resolve required lead handoffs before claiming completion.

Before starting, resolve the exact current `ultra_context` handle. Preserve the selected lead model and effort. Unknown context blocks execution; Plan Mode remains read-only. Existing task scope, repository quality gates and approval requirements still apply.

Before starting workflows, inspect the current chat's MCP App tabs with the supported browser inventory. If an Ultra panel is already open, reuse that exact tab and do not call `ultra_panel`, including when the user opened it manually or you are recovering from an error. A bound dashboard refreshes across turns; inspect its state before deciding another launch is needed. A saved binding alone does not prove a tab is still open, and another chat's panel must never be reused.

Only when this chat has no open Ultra panel, call `ultra_panel` with the verified `contextKey` to bind the dashboard and request display beside the chat. If tab inventory is unavailable and the user says the panel is already open, keep using the bound runtime without another launch; report any blocked visual check. If the host keeps a newly opened app inline, say so and use its Open app in tab control; never claim it opened without host confirmation. Do not ask the user to send a binding message when verified chat routing is available.

In Plan Mode, produce an Ultra plan: the selected lead resolves the design and synthesizes an implementation-ready plan from repository evidence. Use bounded read-only investigations for independent questions where the benefit justifies their total cost. Keep tightly coupled reasoning with the lead. Do not implement the plan, edit project files, dispatch writing workers or publish changes.

The plan must state the outcome and acceptance criteria, the evidence behind the chosen design, precise interfaces and behavior, ordered file-level changes, dependencies, verification and stop conditions. Surface unresolved decisions explicitly. Use `kind: "planning"` for read-only lead handoffs and resolve them only against the plan's acceptance criteria; planning completion does not establish implemented or production-verified behavior. Use arbitrary task phases appropriate to the request; no fixed planning pipeline or critic panel is required.

1. Identify a useful bounded assignment and why its expected benefit exceeds worker input/output, startup, repeated evidence, retries and lead coordination. For example, two independent source checks may save time; a second agent rereading a ten-line patch usually will not. Do not invent savings or token prices.
2. Select an available model and supported effort for that assignment. Start with `gpt-6-luna` for bounded extraction and straightforward checks; use `gpt-6.1-sol` for complex implementation or synthesis. Use `gpt-6-astra` only when substantial uncertainty or consequence justifies the added cost, and record that reason. These are routing starting points, not availability guarantees. The worker backend verifies the live catalog and exact returned model/effort; never substitute silently or retry a blocked model repeatedly.
3. Provide all six assignment fields: outcome, bounded inputs, ownership, constraints, acceptance and stop conditions. Record the seven assessment fields before dispatch and retain them unchanged. Pass source references and relevant extracts, not the parent chat. Reuse completed evidence rather than commissioning the same investigation again.
4. Bound the script with `maxAgentCalls` and an honest lead-session capacity grant. Reserve the lead and other occupied slots. Concurrent workflows share local admission; the grant is not a host-wide reservation. No observed capacity means no invented grant. An observed-token budget warns while a worker runs and blocks later dispatch; never present it as a hard per-worker cap, especially when `maxAgentCalls` is one.
5. Start the immutable script, then use `ultra_wait` across its run IDs. Read results on meaningful changes, completion, errors or lead handoffs. UI polling does not require model calls. Do not turn quiet progress into repeated lead inference or assume silence means a hang.

   Prepare the initial independent assignments before dispatch. Use `parallel()` inside a workflow, or batch independent `ultra_start` calls in one tool execution when separate workflows are useful. Do not finish preparing the second assignment only after starting the first; tool-call latency can accidentally serialize short workers. Verify actual dispatch/start times before claiming work ran concurrently. Dependent follow-ups still start as soon as their own inputs are ready.

6. Keep judgment, required real QA, required review, integration and consequential external actions with the selected lead. Add an independent review only where repository rules or a concrete risk warrant it; no automatic critic teams. Claim and resolve `lead()` handoffs with the exact verified turn, inspect the saved evidence, and distinguish execution completion from goal acceptance. An uncertain worker requires actual termination and write readback before its reconciliation receipt; the old run remains incomplete and never retries automatically.

Worker failures, uncertainty, incomplete acceptance and verification always return to the lead. A panel handoff is never a request for the user to review worker output. Resolve it yourself or preserve an explicit incomplete outcome. Ask the user directly in chat only when an actual decision, missing information or authority is necessary; do not delegate routine verification to them or leave a pending handoff as their next step.

Read [the authoring reference](references/authoring.md) before writing a script. Its APIs and examples describe the implemented runtime. They do not grant missing authority or establish live QA for a particular installation.
